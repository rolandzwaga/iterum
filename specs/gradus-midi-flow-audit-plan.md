# Gradus MIDI Signal-Flow — Remediation Implementation Plan

## Scope

This plan fixes the verified MIDI signal-flow defects in the Gradus step-arpeggiator (host MIDI-in → `Processor::process` → `ArpeggiatorCore::processBlock` → `MidiNoteDelay::process` → `data.outputEvents` + `AuditionVoice`). Every task is self-contained: it restates the bug with `file:line` anchors, specifies an exact regression test that **must be observed failing on current code before the fix**, then the precise edit. Findings were adversarially verified; `CONFIRMED` items get a fix, `PLAUSIBLE` items get a test that doubles as verification (if it passes unchanged, the finding is refuted, the test is kept, no fix is applied). Two shared-engine files (`dsp/include/krate/dsp/processors/arpeggiator_core.{h,cpp}`, `midi_note_delay.h`) are also compiled into **Ruinae**, so edits there carry **CROSS-PLUGIN IMPACT** and must not silently shift the byte-golden MIDI sequences (`tests/test_helpers/midi_golden_compare.h`) used by Gradus (`live_mode_byte_identical_test.cpp`) and Ruinae (SC-004). Default parameter values (humanize 0, strum 0, gate ≤ 100 %) keep those goldens unchanged; any task that legitimately alters output for non-default params must have the goldens regenerated by a human, never quietly.

## GMF-001 — `setupProcessing` between deactivate and reactivate strands sounding arp notes

### A. THE BUG
- File: `plugins/gradus/src/processor/processor.cpp:56-91`; engine `dsp/include/krate/dsp/processors/arpeggiator_core.h:252-269, 638-641`.
- `setActive(false)` records the note-off obligation via `arpCore_.requestPanicNoteOff()` (processor.cpp:74, sets `panicRequested_`/`needsDisableNoteOff_` only — nothing emitted yet), calls `midiDelay_.flushWithNoteOffs()` (:75), and sets `pendingDeactivateFlush_=true` (:76). `setActive(true)` then *skips* `arpCore_.reset()`/`midiDelay_.reset()` when the flush is pending (:62-67).
- Wrong behaviour: if the host inserts `setupProcessing()` between the two (the standard VST3 sample-rate / block-size change sequence, legal only while inactive), `setupProcessing` calls `arpCore_.prepare()` → `reset()` (:87 → arpeggiator_core.h:248), which clears `panicRequested_` (h:262), `needsDisableNoteOff_` (h:261), `currentArpNoteCount_` (h:259) and `heldNotes_` (h:266). The arp's obligation *and* its note list are destroyed, yet `pendingDeactivateFlush_` stays true so `setActive(true)` still skips its reset. `midiDelay_` is untouched by `setupProcessing`, so echo NoteOffs still fire — the two flush paths are now asymmetric. Arp NoteOns emitted before deactivation never get their NoteOffs.
- Correct behaviour: after `deactivate → setupProcessing → activate`, the first `process()` block must emit a NoteOff for every arp NoteOn that was outstanding at deactivation (offCount ≥ onCount per pitch).
- Trigger sequence: Live mode, hold chord [60,64,67], let the arp emit NoteOns; `setActive(false)` → `setupProcessing({sampleRate:48000})` → `setActive(true)` → `process()`.

### B. THE REGRESSION TEST
- Extend `plugins/gradus/tests/unit/processor/set_active_flush_test.cpp`, reusing its `Harness` (line 45) which exposes `noteOn(pitch)`, `runBlock(params)`, and `onCount[128]`/`offCount[128]` tallies.
- `TEST_CASE("GMF-001: setupProcessing between deactivate and reactivate does not strand arp notes", "[gradus][processor][flush]")`
- Drive: Live mode; `noteOn(60); noteOn(64); noteOn(67);` then run enough blocks that arp NoteOns are emitted (assert some `onCount[p] > 0`). Then call `proc.setActive(false)`, `proc.setupProcessing(setup)` with a *changed* `sampleRate`/`maxSamplesPerBlock`, `proc.setActive(true)`, then run one `process()` block.
- Assert: for every pitch `p` with `onCount[p] > 0`, `offCount[p] >= onCount[p]`. (Harness must add a `setupProcessing(ProcessSetup&)` passthrough if not already present.)
- **This test MUST FAIL on current code — run it and confirm the failure before writing the fix.**

### C. THE FIX
- File: `plugins/gradus/src/processor/processor.cpp`, `setActive(TBool)` true-branch (:58-67).
- Before → after: when `pendingDeactivateFlush_` is set on reactivation, re-arm the arp obligation that `setupProcessing`'s `reset()` may have cleared. In the `if (pendingDeactivateFlush_)` branch (:62-63), after clearing the flag, call `arpCore_.requestPanicNoteOff();` so the deferred panic discharge is guaranteed regardless of whether `setupProcessing` ran in between. (This is idempotent — if `setupProcessing` did *not* run, the flags were still set and re-setting is harmless; the panic discharges once at the top of the next `processBlock`.)
- Note the `heldNotes_`/`currentArpNotes_` list cleared by `reset()` means the panic can only release notes the engine still tracks; because `requestPanicNoteOff()`'s `emitPanicNoteOffs` iterates `currentArpNotes_`, and `setupProcessing` cleared it, prefer instead to **not clear the obligation in the first place**: the more robust edit is to guard `setupProcessing` so it does not blow away an outstanding deactivate flush — i.e., in `setActive(true)` re-arm is only a partial fix. **Choose the re-arm approach only if a test confirms `currentArpNotes_` survives; otherwise** make `setupProcessing` skip the `arpCore_.reset()` note-list clear while `pendingDeactivateFlush_` is true (call `arpCore_.prepare()` without `reset()`, or add an `ArpeggiatorCore::prepareKeepingPanic()` that updates `sampleRate_` but preserves `currentArpNotes_`/`panicRequested_`/`pendingNoteOffs_`). Implement whichever makes the test pass; verify by observing `offCount>=onCount`.
- Invariants: do not change the no-`setupProcessing` deactivate/reactivate path already pinned by `set_active_flush_test` F4. Gradus-only file — no golden impact.

## GMF-002 — Sequencer transport stop→play must flush echoes, not reset them

### A. THE BUG
- File: `plugins/gradus/src/processor/processor.cpp:173-176`; `dsp/include/krate/dsp/processors/midi_note_delay.h:100-104, 113-126`.
- On the Sequencer-mode rising transport-play edge (`isSequencer && isPlaying && !wasTransportPlaying_`) the code calls `arpCore_.reset(); midiDelay_.reset();` (:174-176). `midiDelay_.reset()` (midi_note_delay.h:100-104) zeroes `pendingCount_` and `emergencyNoteOffCount_` with no NoteOff emission.
- Wrong behaviour: `midiDelay_.process()` (:208) runs unconditionally every block and drains echoes even while the transport is stopped (`emitDueEchoes` sets `noteOnEmitted=true`; `advanceAndCompact` advances every block — only *arp step generation* is transport-gated at :194). So during a stop, echo NoteOns keep reaching the host with NoteOffs still pending. A stop→play within a long echo tail (long delay + high feedback) then hits `reset()`, discarding echoes whose NoteOn already went out — their NoteOffs are never emitted.
- Correct behaviour: on the rising edge use `midiDelay_.flushWithNoteOffs()` (midi_note_delay.h:113-126) — the same call `setActive(false)` deliberately uses (:75) because the host is still listening. This retains `noteOnEmitted && !noteOffEmitted` echoes with `noteOffRemaining=0`, so the same block's `midiDelay_.process()` emits their NoteOffs at offset 0.
- Trigger: Sequencer mode, MIDI-delay step active (feedbackCount 8, delay 2000 ms Free, high gate scaling). Play blocks so echoes emit; `transportPlaying=false` for 1 block; `transportPlaying=true`. Capture output across the edge.

### B. THE REGRESSION TEST
- Extend `plugins/gradus/tests/unit/processor/sequencer_transport_gating_test.cpp`, reusing its `ProcDriver` (line 53) with per-block `transportPlaying` flag and `CapturedMidi` absolute-sample capture.
- `TEST_CASE("GMF-002: Sequencer stop-then-play flushes in-flight echoes without stranding NoteOffs", "[gradus][processor][transport][echo]")`
- Drive: Sequencer mode; program one active pattern step; configure the MIDI-delay lane step 0 active with `feedbackCount` ≈ 8, Free delay ≈ 2000 ms, high `gateScaling` (via `ParameterChanges` on the delay-lane param IDs). Play several blocks (`transportPlaying=true`) so echo NoteOns appear in captured output; then one block `transportPlaying=false`; then `transportPlaying=true`; then a few more blocks.
- Assert: across the full capture, per pitch `offCount[p] >= onCount[p]` (no stranded echo). Also assert at least one echo NoteOn was captured before the stop (guards against a vacuous pass).
- **This test MUST FAIL on current code — confirm the stranded-NoteOff failure first.**

### C. THE FIX
- File: `plugins/gradus/src/processor/processor.cpp:173-176`.
- Before: `arpCore_.reset(); midiDelay_.reset();`
- After: keep `arpCore_.reset();` (Sequencer pattern restart is intentional per design facts) but replace `midiDelay_.reset();` with `midiDelay_.flushWithNoteOffs();`. The subsequent `midiDelay_.process()` at :208 discharges the retained NoteOffs in the same block.
- Invariants: do not touch the Live-mode branch (it must not reset — design fact). Gradus-only file — no golden impact. `sequencer_transport_gating_test` Stop-only pins still hold (flush of an empty buffer is a no-op).

**Verify:** Standard Verification Block.

## GMF-003 — Emergency NoteOff queue (cap 16) drops NoteOffs under dense eviction

### A. THE BUG — CROSS-PLUGIN IMPACT
- File: `dsp/include/krate/dsp/processors/midi_note_delay.h:388-405` (`addPendingEcho`), cap `kMaxEmergencyNoteOffs = 16` at :435; emit at :408-429.
- On 256-slot ring overflow, eviction of slot 0 is unconditional (shift loop :396-398, `--pendingCount_` :399), but the emergency-NoteOff enqueue for an already-sounded evicted echo (`noteOnEmitted && !noteOffEmitted`) is gated on `emergencyNoteOffCount_ < 16` (:392-394).
- Wrong behaviour: within one block, evictions happen in `process()` pass 1 (`scheduleEchoes` :155-161) while `emitEmergencyNoteOffs` runs in pass 2 (:164), so `emergencyNoteOffCount_` only grows and saturates at 16 during scheduling. Evicting a 17th+ already-sounded echo discards its NoteOff obligation entirely. Reachable across blocks: eviction always steals the oldest (front) slot, and `advanceAndCompact` preserves insertion order, so prior-block sounded-but-unclosed echoes (long gates via `gateScaling` up to 2.0 + high `feedbackCount`) sit at the front and are evicted first by a new dense burst.
- Correct behaviour: every echo NoteOn emitted to the host must get exactly one NoteOff. When the emergency queue would overflow, do not silently drop the obligation.
- Trigger: sustained saturation — many source NoteOns per block at `feedbackCount=16` with long `gateScaling` so >16 front echoes are sounded, then a new dense burst evicts them in one block.

### B. THE REGRESSION TEST
- Extend `dsp/tests/unit/processors/midi_note_delay_test.cpp`, reusing `collectEchoes()`/`filterByType()` (line 41) and its per-pitch tally pattern.
- `TEST_CASE("GMF-003: overflow eviction of >16 sounded echoes never drops a NoteOff", "[midinotedelay][overflow][stuck]")`
- Drive: configure a delay step with `feedbackCount=16`, short delay so echoes sound quickly, `gateScaling` high (≈2.0) so many echoes remain `noteOnEmitted && !noteOffEmitted` across blocks. Feed a burst of ≥20 source NoteOns (distinct pitches) spread over a couple of blocks to fill the 256-slot ring with sounded echoes, then feed a further dense burst in a single block to force >16 sounded evictions. Run enough trailing blocks to drain.
- Assert: every echo NoteOn observed across all blocks has a matching NoteOff (aggregate per-pitch `offCount >= onCount`). Assert `pendingCount() <= kMaxPendingEchoes` throughout (no OOB).
- **This test MUST FAIL on current code — confirm a pitch with unmatched NoteOn first.**

### C. THE FIX
- File: `dsp/include/krate/dsp/processors/midi_note_delay.h`, `addPendingEcho` (:388-405).
- Before → after: when the evicted slot is a sounded, unclosed echo *and* the emergency queue is full (`emergencyNoteOffCount_ >= kMaxEmergencyNoteOffs`), do **not** drop its NoteOff. Preferred edit: apply back-pressure — refuse to evict/add the new echo when doing so would strand a NoteOff and the emergency queue is full (i.e., early-`return` from `addPendingEcho` before the eviction, leaving the sounded echo in place; a later block drains it). This preserves the invariant that a scheduled-and-sounded echo is never discarded. Alternative (larger change): size `emergencyNoteOffs_` to the worst-case per-block steal count. Choose the back-pressure early-return; it is minimal and keeps the buffer bounded. Confirm the newly-added echo being dropped (not the sounded one) is acceptable — dropping a fresh, never-sounded NoteOn is the correct sacrifice (checklist: dropping a NoteOff is far worse than dropping a NoteOn).
- Invariants: keep the 256 ring cap and the existing `emitEmergencyNoteOffs` retain-on-starve logic (:422-428) intact. MidiNoteDelay is Gradus-only functionally, but the file lives under `dsp/` — run `dsp_processors_tests` and `ruinae_tests`.

**Verify:** Standard Verification Block **+ CROSS-PLUGIN** (`dsp_processors_tests`, `ruinae_tests`).

## GMF-004 — Host velocity-0 NoteOn must be treated as NoteOff

### A. THE BUG
- File: `plugins/gradus/src/processor/processor.cpp:114-129` (input drain), engine `arpeggiator_core.h:277-303`.
- The drain unconditionally routes every `kNoteOnEvent` to `arpCore_.noteOn(pitch, (uint8_t)(velocity*127))` (:119-122). A vel-0 NoteOn becomes `noteOn(pitch, 0)`, which increments `physicalKeysHeld_` (h:278) and stores the note in `heldNotes_` (h:303). `HeldNoteBuffer` does not enforce velocity≠0.
- Wrong behaviour: MIDI running-status note-off is a NoteOn with velocity 0. A source that forwards the raw vel-0 NoteOn *and* treats it as the release never sends a `kNoteOffEvent`, so the pitch stays in `heldNotes_` and arps forever, and `physicalKeysHeld_` is permanently over-counted (corrupting latch-Hold "all keys released" detection at h:337-343 and the empty-held short-circuit).
- Correct behaviour: velocity==0 (MIDI-1.0) NoteOn is a note-off for that pitch.
- Trigger: Live mode, empty buffer; host sends `kNoteOnEvent(pitch=60, velocity=0.0)` as the key release; run several blocks → pitch 60 must not arp.

### B. THE REGRESSION TEST
- New file `plugins/gradus/tests/unit/processor/velocity_zero_noteon_test.cpp` (add to `plugins/gradus/tests/CMakeLists.txt`), reusing the `Harness` pattern from `set_active_flush_test.cpp:45` and `Krate::Test::EventList` (`addNoteOn`/`addNoteOff`, noteId −1).
- `TEST_CASE("GMF-004: velocity-0 NoteOn is treated as a NoteOff and does not strand a held note", "[gradus][processor][velocity]")`
- Drive: Live mode. Block 1: `EventList.addNoteOn(60, 0.5f)` → run, expect pitch-60 arp emission begins. Block 2: `EventList.addNoteOn(60, 0.0f)` (raw vel-0 NoteOn, no `addNoteOff`) → run several more blocks.
- Assert: after the vel-0 event, arp output for pitch 60 stops within a bounded number of blocks (no new NoteOn(60) after its gate), and per-pitch `offCount[60] >= onCount[60]`. Optionally expose `arpCore_.heldNotes()` to assert pitch 60 is no longer held.
- **This test MUST FAIL on current code — confirm pitch 60 keeps arping first.**

### C. THE FIX
- File: `plugins/gradus/src/processor/processor.cpp:119-122`.
- Before → after: branch on velocity in the `kNoteOnEvent` case — if `e.noteOn.velocity <= 0.0f`, call `arpCore_.noteOff(static_cast<uint8_t>(e.noteOn.pitch))` instead of `noteOn(...)`.
- **CAUTION (do not over-reach):** this is the MIDI-1.0 running-status convention. A genuine MIDI-2.0 UMP vel-0 note-on is a real note-on; Gradus's input path here is the legacy VST3 `Event` path, so `velocity<=0 → noteOff` is correct for it. Do not alter any UMP/AU path. Gradus-only file — no golden impact (goldens use non-zero velocities). Mirror is the shared `midi_event_dispatcher.h` convention used by Ruinae; do not refactor Gradus onto it in this task (surgical change only).

## GMF-005 — Chord/ratchet replace paths must cancel pending NoteOffs first

### A. THE BUG — CROSS-PLUGIN IMPACT
- File: `dsp/include/krate/dsp/processors/arpeggiator_core.cpp:1013-1020` (ratchet first sub-step, `!isSlide` replace) and `:1122-1129` (chord replace).

Every other path that manually releases `currentArpNotes_` cancels pending offs first: euclidean-rest (:624), condition-fail (:666), modifier-rest (:717), tie (:748), slide (:1076).

- Trigger: ArpMode Chord (or chord lane >1 note), gateLength 200 %, two consecutive steps whose expanded chords share a pitch (e.g. both contain 60).

## GMF-006 — 128-event cap must guard tracking + scheduling, not just NoteOn emission

### A. THE BUG — CROSS-PLUGIN IMPACT
- File: `dsp/include/krate/dsp/processors/arpeggiator_core.cpp` — single-note path `:1160-1182`, chord path `:1134-1156`. `maxEvents = min(spanSize, 128)` (`:19-21`; processor passes `arpEvents_[128]`).
- NoteOn writes are guarded by `eventCount < maxEvents` (:1134, :1160), but the `currentArpNotes_` tracking (:1143-1146, :1173-1175) and `addPendingNoteOff` scheduling (:1152-1156, :1180) run without an `eventCount` guard. `addPendingNoteOff` (h:1205-1228) unconditionally appends to `pendingNoteOffs_` (not the output span).
- Wrong behaviour (phantom off): when the span saturates mid-step, a NoteOn is dropped yet the note is tracked as sounding and a pending NoteOff is scheduled → later `emitDuePendingNoteOffs` emits a NoteOff for a note that never sounded (routed to host + mono audition).
- Wrong behaviour (stuck note): the chord/ratchet replace-NoteOff loops (:1125-1128, :1014-1019) are `eventCount`-guarded but set `currentArpNoteCount_=0` unconditionally (:1129, :1019). If the previous step was Tie/Slide (`suppressGateNoteOff`, so those notes have **no** pending off) and the cap truncates the replace-NoteOff loop, the tied notes are erased from tracking with no output NoteOff and no pending NoteOff — unreleasable even by a panic flush.
- Correct behaviour: a dropped NoteOn must not leave a scheduled/tracked NoteOff; a note is removed from `currentArpNotes_` only after its release NoteOff was actually emitted (or is still guaranteed by a pending off).
- Trigger: Live mode, hold a 16–32-note chord, ArpMode Chord, fast free rate, large block (≥4096) so eventCount crosses 128 mid-step; for the stuck variant, program the modifier lane so a Tie/Slide step precedes a chord step.

### B. THE REGRESSION TEST

(Core-only tests cannot see the processor's 128 span; the F6 MidiNoteDelay test shrinks a different span.)
- `TEST_CASE("GMF-006: 128-event cap never emits a phantom NoteOff nor strands a tied note", "[gradus][processor][overflow][stuck]")`

Assert: no pitch has more NoteOffs than NoteOns, and no NoteOff is emitted for a pitch that had no preceding emitted NoteOn.
- Drive part 2 (stuck): program modifier lane so a Tie step precedes a chord step, big chord, force the cap during the chord replace loop; run trailing blocks. Assert per-pitch `offCount >= onCount`.
- **This test MUST FAIL on current code — confirm the phantom/stranded off first.**

### C. THE FIX
- File: `arpeggiator_core.cpp`. Move the `currentArpNotes_` tracking store (chord :1143-1146, single :1173-1175) and the `addPendingNoteOff` scheduling (:1152-1156, :1180) **inside** the same `eventCount < maxEvents` condition that guards each NoteOn — i.e., a note is tracked/scheduled only if its NoteOn was actually written. For the replace loops (:1125-1128, :1014-1019): only set `currentArpNoteCount_=0` after confirming all replace NoteOffs were emitted; if the loop truncated at the cap, keep the un-released notes in `currentArpNotes_` so a later panic/stop flush can release them (do not blindly zero the count). Simplest robust form: track how many replace offs were emitted and compact `currentArpNotes_` to the un-released remainder instead of zeroing.
- Invariants: `pendingNoteOffs_` cap stays 64 (h:166); `currentArpNotes_` bound stays 32. Under-full blocks (the overwhelming common case) are unaffected → goldens unchanged; verify `ruinae_tests` + `live_mode_byte_identical_test` green. Zero-heap/noexcept preserved (no allocation added).

## GMF-007 — Clamp strum/humanize-augmented NoteOn offsets to `[0, blockSize)`

### A. THE BUG — CROSS-PLUGIN IMPACT
- File: `dsp/include/krate/dsp/processors/arpeggiator_core.cpp` emission sites `:336` (`fireSubStep`), `:1030` (ratchet first sub-step), `:1088` (chord slide), `:1139` (chord). Each emits `.sampleOffset = humanizedSampleOffset + strumOffsetFor(i)` (or `sampleOffset + strumOffsetFor(i)`).

The processor copies `evt.sampleOffset` verbatim to `data.outputEvents` (processor.cpp:222) and `MidiNoteDelay::process` passes through / sorts but never clamps — the out-of-`[0,numSamples)` NoteOn reaches the host (dropped or the whole list rejected). The paired gate NoteOff is deferred in-range, so the note is silently lost.
- Correct behaviour: every output event `sampleOffset` ∈ `[0, numSamples)`.
- Trigger: `kArpStrumTimeId` ≈ 50 ms, hold a 3-note chord in Chord mode, 64-sample block at 48 kHz, step near block start.

- Assert: for **every** event in `data.outputEvents`, `0 <= sampleOffset < numSamples`.
- **This test MUST FAIL on current code — confirm an offset ≥ 64 first.**

### C. THE FIX
- File: `arpeggiator_core.cpp`. At each of the four sites, clamp the final offset: `std::clamp(humanizedSampleOffset + strumOffsetFor(i), 0, static_cast<int32_t>(blockSize) - 1)`.
- Implementation wrinkle: `fireStep` receives `blockSize` (signature includes it); `fireSubStep` (:303-307) does **not** — thread `blockSize` into `fireSubStep` (add the param and update its two call sites at :275 and :294) **or** store the last block size in a member set at the top of `processBlock`. ## GMF-012 — Speed-curve staging must be a real double buffer (fix the message/audio data race)

### A. THE BUG — CROSS-PLUGIN IMPACT
- File: `arpeggiator_core.h:674-695` (`setLaneSpeedCurveTable` / `consumePendingCurveTables`), state `:1559-1561`.
- `setLaneSpeedCurveTable` (message thread) does a plain 1 KB copy into the single `laneSpeedCurveTablesStaging_[laneIndex]` then `dirty.store(release)`. `consumePendingCurveTables` (audio thread) acquire-loads dirty and plain-copies the **same** staging slot into the active table, then relaxed-clears dirty. There is exactly one staging slot per lane.
- Wrong behaviour: the release/acquire on the dirty flag serializes one write→read handoff but does **not** serialize a second message-thread write against an in-progress audio-thread copy of the same slot — a C++ data race / UB on the audio thread (violates the RT thread-safety rule). Practically bounded (garbled 256-entry curve feeding a speed clamped to [0.1,8.0], no crash/stuck note), but a relaxed `dirty=false` landing after a racing `dirty=true` can persist the garbled table across blocks. Triggered by dragging a speed-curve point during playback (~30–60 Hz IMessages) or a `setState` preset load during playback.
- Correct behaviour: lock-free handoff of a >atomic-width payload via a genuine double buffer with an atomic published index (or a seqlock), so the message thread never writes the slot the audio thread is reading.

### B. THE REGRESSION TEST
- New file `dsp/tests/unit/processors/arpeggiator_core_curve_race_test.cpp` (add to `dsp_processors_tests` in `dsp/tests/CMakeLists.txt`). This is a concurrency/tearing test, not a golden.
- `TEST_CASE("GMF-012: concurrent curve-table publish never yields a torn active table", "[arpeggiatorcore][rtsafety][curve][.race]")`
- Drive: one thread hammers `setLaneSpeedCurveTable(lane, tableA)` / `tableB` in a tight loop where `tableA` is all-0.0 and `tableB` is all-1.0; another thread calls `consumePendingCurveTables()` in a loop and, after each consume, reads the active table (via a test accessor) and asserts every element is exactly 0.0 or exactly 1.0 (never a mix). Run for a bounded iteration count.
- Note: build (or document) a ThreadSanitizer/valgrind run of this test as the real detector; the value-mixing assertion is the portable proxy. **On current single-buffer code the mixing assertion may pass by luck (aligned float writes are atomic), so treat a clean TSan report as the authoritative pre-fix failure signal.** If neither the assertion nor TSan flags it in this environment, record that and still apply the double-buffer fix (the data race is source-confirmed).
- **Run first and record the result (TSan race report expected on current code).**

### C. THE FIX
- File: `arpeggiator_core.h`. Convert `laneSpeedCurveTablesStaging_` to two slots per lane (`std::array<std::array<std::array<float,256>,2>, kNumLanes>`) plus a per-lane `std::atomic<uint8_t> stagingWriteIndex_` (or a single atomic "published slot" index). `setLaneSpeedCurveTable` writes the inactive slot then publishes the index with `release`; `consumePendingCurveTables` acquire-loads the index and copies from the published slot. Keep the existing dirty-flag gating or fold it into the index. Preserve the public method signatures.
- Invariants: audio thread still lock-free, no allocation. Fix the stale contract comments (h:668-671 "Safe to call from any thread" / SKILL "double-buffered off-thread") to describe the real double buffer. CROSS-PLUGIN: Ruinae also drives curve tables — run `ruinae_tests`.
